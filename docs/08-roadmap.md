# 開発計画・ロードマップ

## 1. 計画の考え方

本計画は初版の現状と、次の改善を判断するための順序を整理する。
公開日、予算、開発人数、契約サービスは未指定であり、固定した日程や購入を前提にしない。
将来案は実装済みの機能として扱わず、必要な情報と完了条件が揃った段階で着手範囲を決める。

中心の目的は「観測された飛行中機数を把握し、気になった機体の観測値を確認できること」である。
改善を追加する場合も、機数の定義、データの鮮度、情報源、欠損値の表示を保つ。

## 2. 現在の初版に含まれるもの

| 分野 | 現在の実装 |
| --- | --- |
| フロントエンド | React、TypeScript、Vite、日本語ダッシュボード |
| 地図 | Leaflet、機体選択、検索反映、最大 1,200 機の描画 |
| 一覧 | callsign・ICAO24・登録国検索、並び替え、8 件のページ切替 |
| 詳細 | 位置、高度、対地速度、地上航跡、垂直速度、最終受信 |
| API | Express、状態確認、ダッシュボード、ICAO24 詳細 |
| データ取得 | OpenSky、匿名取得、OAuth、キャッシュ、制限時の待機 |
| 状態表示 | ライブ、最終取得データ、取得不可、明示的デモ |
| 保存 | SQLite、モード別の最新観測、短期の機数履歴 |
| 開発 | PowerShell / npm からの導入・起動、型確認、テスト、ビルド |
| 文書 | 企画、要件、画面、構成、DB、API、テスト、導入、GitHub 手順 |

API 取得は要求に応じて実行するため、画面を閉じたままの継続収集は初版に含まれない。
利用者向け認証、空港、路線、お気に入り、機体別の航跡は現在の提供機能に含まれない。

## 3. 優先度の定義

| 優先度 | 意味 |
| --- | --- |
| P0 | 現在の目的を使える状態にするため、導入・検証時に必要 |
| P1 | 実利用または公開の前提条件に応じて優先する改善 |
| P2 | 利用者の要望と実現性を確認した後に追加する機能 |
| P3 | 利用規模や運用上の必要性が出た場合に検討する拡張 |

優先度は作業の期限を表さない。
外部 API の利用資格、利用規約、データの提供範囲が機能の前提になる場合は、その確認を先に行う。

## 4. 段階 1：既存フォルダーで初版を使う（P0）

ソース、設定例、文書を用意済みの `global-flight-monitor` フォルダーに配置する。
Node.js 24.5.0 以上で依存関係を導入し、DB を初期化し、開発サーバーを起動する。
自動セットアップを利用する場合も、依存導入・DB 初期化・ビルドの失敗を確認できるようにする。
`npm run setup` または `scripts/setup.ps1` はこれらの準備をまとめて実行する。
開発起動には `npm run dev` または `scripts/start.ps1` を利用する。

| 作業 | 完了条件 |
| --- | --- |
| 配置 | `package.json`、`src`、`server`、`docs` が既存フォルダーの直下にある |
| 依存導入 | `npm ci` がロックファイルを変更せず成功する |
| DB 初期化 | `data/flights.sqlite` が作成され、繰り返しても利用できる |
| 開発起動 | 画面と API が起動し、ブラウザーから利用できる |
| ライブ | 利用可能な接続条件で実データを取得し、時刻と情報源を確認できる |
| エラー時 | 取得不可または最終取得データの説明があり、誤った実測値を表示しない |
| デモ | 明示的選択で地図・一覧・詳細を試せる |
| GitHub 準備 | ソース・文書を追加でき、秘密値・DB・生成物を含めない |

この段階は利用者の Windows 端末で最終確認する。
クラウド上の検証が成功しても、個々の端末のファイアウォール、Node.js のバージョン、ポート使用状態は別に確認する。

## 5. 段階 2：初版の受入と再現性を固める（P0）

| 確認 | 完了条件 |
| --- | --- |
| 集計 | API と機数が一致し、地図件数や検索結果と混同しない |
| 詳細 | 地図・一覧から同じ機体を選び、値・単位・欠損を確認できる |
| 検索 | callsign、ICAO24、登録国、0 件、検索解除を確認する |
| モード | 連続切替でもデモと実観測の応答を混ぜない |
| 鮮度 | 120 秒超の観測を古いデータとして表示する |
| 再起動 | 前回の実観測と通常の次回取得期限を引き継ぐ |
| ブラウザー | PC・390 px で検索・詳細・モード選択を操作できる |
| ビルド | 型確認とビルドが成功し、`npm start` で利用できる |

API が利用できないときは、原因と影響範囲を記録する。
デモ成功だけで外部 API の取得成功とみなさず、外部 API が不安定なことだけで操作機能の検証を止めない。
確認結果は実行コマンドとともに残し、性能や可用性について未計測の数値を達成済みと記載しない。

## 6. 段階 3：データ更新と理解しやすさを改善する（P1）

匿名利用は標準 900 秒の取得間隔で、観測の鮮度期限は 120 秒である。
継続的に最新の観測を表示したい場合は、OAuth の利用条件と必要な取得量を確認する。
単に画面の確認頻度を上げても、外部 API の取得頻度や観測精度は改善しない。

| 候補 | 着手前に決めること | 完了条件の例 |
| --- | --- | --- |
| OAuth 利用 | API クライアントの用意、利用枠、秘密値の管理 | サーバーだけで認証し、期限と制限を守る |
| 時刻表示の改善 | 日付、UTC／日本時間、好みの保持 | 観測・取得・受信時刻の意味が区別できる |
| 地上機の表示 | 集計範囲、API 契約、UI の用語 | 「すべて」で返す対象と機数の定義が一致する |
| 検索の改善 | 対象項目、日本語国名、絞り込み条件 | 欠損と検索結果の扱いをテストできる |
| 地図の改善 | クラスタ、地域絞り込み、選択維持 | 大量の機体でも実測した基準で操作できる |

現在の「すべて」切替は、API が返す飛行中機体全体を示す。
地上機を追加する場合は、画面の切替だけでなく API、統計、保存、テストを一緒に変更する。

## 7. 段階 4：公開環境の準備（P1、公開する場合）

公開先はまだ指定されていないため、特定のサービスや料金プランを確定しない。
単一サーバー構成では、SQLite の永続保存領域と Node.js の常時起動条件を確認する。

| 準備 | 決める項目・確認 |
| --- | --- |
| 実行環境 | Node.js のバージョン、起動コマンド、プロセス再起動 |
| 外部接続 | npm、OpenSky、OAuth、地図タイルへの接続 |
| 公開 URL | ドメイン、HTTPS、リバースプロキシ、ポート |
| 永続データ | DB 保存先、容量、再デプロイ時の扱い |
| 秘密値 | 環境設定、権限、漏えい時の更新方法 |
| バックアップ | 保存先、頻度、復元手順、復元の試験 |
| 監視 | API の稼働と上流取得の状態を区別して監視 |
| 運営表示 | 情報源、受信範囲、利用条件、問い合わせ方法 |
| 受入 | 想定アクセス数を決め、応答・描画・DB の負荷を計測 |

健康状態 API が正常でも、OpenSky が取得不可である場合がある。
画面が表示できることと、新しい実観測を取得できることを別々に監視する。
公開の完了は、URL から利用でき、永続化・再起動・復元・秘密値の除外を実際に確認した時点で判断する。

## 8. 段階 5：利用者向け機能を追加する（P2）

| 将来の機能 | 必要な判断・依存 |
| --- | --- |
| お気に入り | 端末内保存かアカウント保存か、対象は機体か便か |
| ユーザー登録・ログイン | 認証方式、ユーザー情報、削除、運用責任 |
| 空港・出発到着・路線 | 別 API やデータセットの利用条件、識別子との対応精度 |
| 機種・航空会社・登録番号 | 補完データの出典、更新頻度、欠損・不一致の扱い |
| 機体の航跡 | 位置履歴の保存頻度、保持期間、容量、古い位置の説明 |
| 通知 | 何を検知するか、重複通知、許可、配信手段 |
| データ出力 | 対象項目、期間、個数、提供元の再配布条件 |

callsign の文字列だけから出発・到着空港や航空会社を確定しない。
機体識別子と日々の運航便の識別子を分け、対応情報の確度を表す。
追加機能は仕様、保存方式、API、画面、テストを揃えてから提供する。

## 9. 段階 6：収集・保存・性能を拡張する（P3）

利用規模が増える場合は、現在の一つの Node.js プロセスの取得共有だけでは不十分になる。
複数プロセス間の取得制御、スケジュール、共有キャッシュ、データ保持を設計する。
DB を変更する場合は、移行の必要性を計測で確認し、データ移行と戻し方を用意する。

| 候補 | 完了条件の例 |
| --- | --- |
| 継続収集 | 閲覧がない時間も取得し、制限と失敗の再試行を制御できる |
| 長期統計 | 保持期間、集約方法、欠測を決め、保存量を確認する |
| 共有取得 | サーバー数が増えても上流の利用枠を重複消費しない |
| 描画の改善 | 対象端末と機体数を決め、現状と改善後の結果を比較する |
| DB の移行 | 既存観測・履歴を失わず移行し、復元方法を試す |

現在の履歴はモードごとに 24 時間・最大 1,440 点、API 応答は直近最大 360 点である。
「24 時間保存」を、常に 24 時間の連続観測があることと解釈しない。

## 10. 各段階の共通完了条件

1. 追加・変更する目的と受入条件が文書に記載されている。
2. 観測の範囲、時刻、欠損値、ライブとデモの区別が保たれている。
3. API と DB の変更は再起動・既存データとの関係を確認している。
4. 変更に対応する型確認、テスト、ビルドが成功している。
5. 秘密値、DB、依存関係、生成物が GitHub や配布物に含まれない。
6. 実際に確認したことと、未計測・未設定のことが区別されている。
7. 導入手順と関連文書が同じ変更に合わせて更新されている。
