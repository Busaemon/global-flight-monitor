# 要件定義書

## 1. 文書の基準

本書は現在の初版のソースを基準に、提供する機能と受入条件を定義する。
ユーザーの要望は、世界の飛行中機数の確認、機体詳細の確認、DB・バックエンド・フロントエンドの制作、既存フォルダーへの配置、GitHub 用文書の用意である。
OpenSky、SQLite、画面の構成、保存期間、取得間隔は、この要望を実現するための初版の設計判断である。

実装済みは「ソースに存在する」ことを示す。
特定の端末、外部 API、公開環境での受入完了は、[テスト仕様](07-test-specification.md)に従って別途確認する。

## 2. 用語と集計範囲

| 用語 | 定義 |
| --- | --- |
| 観測時刻 | OpenSky の応答に含まれる状態ベクトル全体の基準時刻 |
| 取得時刻 | サーバーが観測を取得して保存した時刻 |
| 最終受信 | 機体の通信を最後に受信した時刻 |
| 位置更新時刻 | 機体の位置情報の基準時刻 |
| 飛行中機体 | 有効な状態ベクトルで `on_ground=false` の機体 |
| ICAO24 | 機体を識別する 6 桁の 16 進数の識別子 |
| callsign | 状態ベクトルの通信上の呼出符号。旅客向け便名との一致は保証しない |
| 登録国 | `origin_country`。現在位置や出発地の国を意味しない |
| ライブ | 外部 API から取得した実データのモード |
| デモ | 操作確認のために生成した架空データのモード |

飛行中機数は、受信情報が観測時刻から 120 秒以内にあり、未来側への差が 30 秒以内の機体を対象にする。
同じ ICAO24 は重複計上せず、最新の最終受信を採用する。
全世界の正確な総数の保証は対象外である。

## 3. 機能要件と受入条件

### FR-01 観測数と統計

飛行中機数、有効な位置を持つ機体数、登録国数、平均高度を表示する。
平均高度は値がある飛行中機体だけを対象にする。

- 受入条件：API の `stats.airborne` と画面の主な機数が一致する。
- 受入条件：検索や地図の間引きを行っても、全体の統計は変化しない。
- 受入条件：取得できず保存済みデータもないとき、画面は「—」を表示し、0 機と断定しない。

### FR-02 世界地図

新しい有効な緯度・経度がある機体を地図上に表示する。
地図には最大 1,200 機を間引いて描画し、表示件数と間引きの説明を示す。

- 受入条件：位置がない機体は地図に表示せず、機数・一覧からは除かない。
- 受入条件：地図の表示件数が機数の統計と異なる場合でも、両者を同じ総数として表示しない。
- 受入条件：マーカーの向きは取得した地上航跡を使い、マーカーを押すと詳細が表示される。
- 受入条件：詳細地図の取得に失敗しても、簡易背景と機体の操作を利用できる。

### FR-03 検索・並び替え・ページ切替

callsign、ICAO24、登録国の文字列を大文字小文字を区別せず部分一致で検索する。
便名順、高度が高い順、速度が速い順を選べる。一覧は 1 ページ 8 件である。

- 受入条件：前後の空白を除いた検索語を同じ条件で地図と一覧に適用する。
- 受入条件：検索・並び順・モードを変更したら一覧の先頭ページに戻る。
- 受入条件：0 件の場合は検索結果がないことを示し、検索の解除を実行できる。
- 受入条件：API が返した飛行中の機体を対象に検索・並び替えを行う。地上機は含めない。

### FR-04 機体詳細

地図または一覧から選んだ ICAO24 の最新保持レコードを詳細欄に表示する。

- 受入条件：callsign、ICAO24、登録国、高度、対地速度、地上航跡、垂直速度、緯度・経度、最終受信、位置取得方法が確認できる。
- 受入条件：callsign がない場合は ICAO24 を表示名として使う。
- 受入条件：高度・速度などの欠損値は「—」、緯度・経度の欠損は「未取得」を表示する。
- 受入条件：位置がない場合は「地図で位置を確認」を押せない。
- 受入条件：閉じる操作またはデータモード変更で選択を解除する。

### FR-05 単位と情報の意味

- 受入条件：高度は m、対地速度は km/h、垂直速度は m/s、地上航跡は ° で表示する。
- 受入条件：API の速度 m/s は画面で 3.6 倍して km/h に変換する。
- 受入条件：高度は幾何高度を優先し、欠損時に気圧高度を使用する。
- 受入条件：登録国を飛行場所として説明せず、位置取得方法と情報源を確認できる。

### FR-06 状態と鮮度

API の状態は `live`、`stale`、`unavailable`、`demo` を使用する。
画面は初回読込、ライブ、保存済みの古い観測、取得不可、明示的なデモを区別する。

- 受入条件：観測から 120 秒を超えたライブ情報は、次の通信を待たず最終取得データの表示に切り替わる。
- 受入条件：取得に失敗しても同じモードの保持データがあれば、時刻と説明を付けて表示する。
- 受入条件：保存済みデータがなければ取得不可として、再取得とデモ選択を案内する。
- 受入条件：観測時刻と取得時刻を分け、画面の時刻には UTC を明記する。

### FR-07 取得間隔と制限

匿名は標準 900 秒、OAuth 設定時は標準 120 秒で上流取得する。
ブラウザーは標準設定でライブ状態を 30 秒ごと、デモを 10 秒ごと確認する。

- 受入条件：手動更新や複数の同時閲覧でも、同一プロセスの上流取得期限を守る。
- 受入条件：同時に必要になったライブ取得は一つの実行を共用する。
- 受入条件：429 を受けた場合は提供元の待機情報を反映し、保持データか取得不可を返す。
- 受入条件：再起動後も保存済み取得時刻を参照し、通常の取得期限前に不要な上流取得をしない。

### FR-08 明示的なデモ

- 受入条件：ユーザーの選択でのみデモへ切り替え、外部 API エラーだけで自動移行しない。
- 受入条件：架空の機数・位置・機体情報である旨をバナー、情報源、履歴に示す。
- 受入条件：実データとデモを DB・API・画面で区別し、異なるモードの遅延応答を表示しない。
- 受入条件：前回選択したモードを保存できる場合は次回起動時に復元する。保存できなくても操作を継続できる。

### FR-09 保存と履歴

SQLite にモードごとの最新観測と飛行中機数の履歴を保存する。

- 受入条件：再起動後に前回の実観測を最終取得データとして利用できる。
- 受入条件：機体更新と履歴更新はトランザクション内で行い、途中失敗を部分保存しない。
- 受入条件：履歴はモードごとに観測時刻基準で 24 時間、最大 1,440 点を保持する。
- 受入条件：API は直近最大 360 点を時刻順で返し、グラフは 2 点以上で描画する。
- 受入条件：履歴が不足するときは蓄積中の表示を行い、未収集区間の実測値を作らない。

### FR-10 API と開発環境

- 受入条件：`/api/health`、`/api/dashboard`、`/api/flights/:icao24` を利用できる。
- 受入条件：不正なモードや識別子を 400、該当機体がない場合を 404 で返す。
- 受入条件：Node.js 24.5.0 以上で依存導入、DB 初期化、開発起動、テスト、ビルドを実行できる。
- 受入条件：`npm run setup` で依存導入、DB 初期化、型確認、ビルドを実行し、失敗時は次の工程に進まない。
- 受入条件：PowerShell の補助スクリプトからセットアップ・開発起動・ビルド済み起動を実行できる。
- 受入条件：既存フォルダーへ必要なファイルを置いて利用でき、フォルダーを二重に作成する必要がない。
- 受入条件：企画・要件・画面・構成・DB・API・テスト・開発計画を Markdown として GitHub に追加できる。

## 4. 非機能要件

| ID | 要件・現在の方針 | 評価方法と限界 |
| --- | --- | --- |
| NFR-01 | OAuth の秘密値をサーバー側だけで扱う | 画面バンドル・配布物・Git 差分に含まれないことを確認 |
| NFR-02 | `.env`、DB、依存関係、生成物を Git 対象から除く | `git status` と配布物の内容を確認 |
| NFR-03 | HTTPS、証明書確認、通常の npm 整合性確認を維持する | 接続・インストール時に検証を無効にしない |
| NFR-04 | 日本語 UI と UTC の観測時刻を提供する | 画面の文言、数値、単位を確認 |
| NFR-05 | PC と狭い画面で主要操作を利用できる | 1440 px と 390 px のブラウザーテストを基準に確認 |
| NFR-06 | 主要ボタン・入力にラベルとフォーカス表示を付ける | キーボード操作と支援用ラベルを確認。適合認証は未実施 |
| NFR-07 | 描画対象を最大 1,200 機に抑える | 件数・選択維持を確認。描画時間の合格値は未計測 |
| NFR-08 | キャッシュと同時取得の共用で API 利用を抑える | 間隔・並列アクセスのテストで確認 |
| NFR-09 | TypeScript の型確認とテストを継続可能にする | `npm test`、`npm run build`、ブラウザーテストで確認 |
| NFR-10 | OpenStreetMap、CARTO、Natural Earth の帰属を残す | 画面とソースに帰属があることを確認 |

性能について、同時利用者数、応答時間の百分位、CPU・メモリー、通信量の保証値は設定していない。
地図上限とキャッシュは現在の設計値であり、負荷試験の結果ではない。
24 時間稼働、障害復旧時間、データ復旧範囲の保証は、公開環境の運用要件を決めた後に評価する。

## 5. 初版で扱わない要件

ユーザー登録・ログイン、お気に入り、空港、路線、出発・到着予定、旅客数、運賃、予約、遅延通知は実装対象に含めていない。
機体別の過去位置保存、航跡再生、長期統計、CSV 出力、複数サーバーでの取得共有も将来の候補である。
地上機を含む検索・一覧は提供しない。
外部 API のアクセス条件が満たされない場合に、欠けた実データを推測して補うことはしない。

## 6. 前提と受入手順

1. 既存フォルダーにソースと設定例を配置し、Node.js のバージョンを確認する。
2. `npm run setup` を実行する。個別に実行する場合は `npm ci`、`npm run db:init`、`npm run build` を使う。
3. `npm run dev` で API と画面を起動する。
4. ライブ状態、取得不可、明示的デモ、検索、選択、単位、時刻を確認する。
5. `npm test`、`npm run build`、必要なブラウザーテストを実行する。
6. `npm start` でビルド済み画面と API を同じポートから利用する。
7. Git に秘密値と DB が含まれないことを確認して文書・ソースを追加する。

詳細な確認項目は[テスト仕様](07-test-specification.md)、公開前の追加作業は[開発計画](08-roadmap.md)を参照する。
既存フォルダーへの配置は[Windows のセットアップ](09-windows-setup.md)、アップロードは[GitHub への追加](10-github-guide.md)を参照する。
本書を変更した場合は[画面仕様](03-screen-specification.md)、[構成設計](04-architecture.md)、[DB 設計](05-database-design.md)、[API 仕様](06-api-specification.md)も合わせて更新する。
